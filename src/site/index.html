Service Status

How it works

A scheduled GitHub Actions job checks every service about every 5 minutes. GitHub can delay scheduled runs, so gaps of 10 to 15 minutes are normal.

  • Vendor status checks read the vendor's official status feed. Accurate, but vendors often post late.
  • Direct probes load a real login page or API from GitHub's servers. These usually catch problems first. A probe only counts as failed if it fails twice, 15 seconds apart.
  • History bar: each block is 30 minutes, oldest on the left. Its color is the worst result in that window. Gray means no check ran. Hover a block for details. The percentage is the share of checks that were working.
  • Response time (direct probes only): how long the page took to load over the last 24 hours. The scale starts at 1 second, so a flat line near the bottom is healthy. The dashed line is the slow limit when it's in range. Gaps are failed checks. Hover for exact times.
  • Tile view is for a wall screen. Add ?view=tv to the address for a full-width version with bigger text.
  • Alerts go to Teams and phone push only when something changes: a new problem, a worse problem, a new incident, or recovery.
  • Can't check means the status source itself could not be read 3 runs in a row. Not configured means the check needs credentials first.
